# 갈피 기능명세서 수동 테스트 가이드

## 파일과 사용 목적

- 업로드할 파일: `galpi-feature-spec-issue-fixture.pdf`
- 이 가이드는 평가자용이다. LLM 입력이나 업로드 PDF에 함께 넣지 않는다.
- 10페이지, 명시적인 섹션 7개, 서로 다른 기능 ID 32개로 구성했다.
- 기능대조 결과 목록 조회는 같은 ID로 7~8페이지에 이어진다. 문서에 등장하는 기능 제목은 33회지만 별개 기능은 32개다.
- 현재 소스와 PR-AnalyzerV20 와이어프레임을 바탕으로 만든 **합성 테스트 명세서**다. 실제 운영 명세나 구현 완료 목록이 아니다.
- 2~9페이지는 기존 백엔드와 이번 기능대조 개발 내용을 중심으로 작성했다. 10페이지에는 와이어프레임의 공유·내보내기 확장 요구사항 및 의도적 결함을 배치했다.
- 와이어프레임의 샘플 서비스에 등장하는 회원가입·채팅·게시판 요구사항은 갈피 자체의 기능이 아니므로 옮기지 않았다.

## 1. 의도적으로 심은 특이사항

| 유형 | 원문 위치 | 의도적 결함 | 확인할 결과 |
|---|---|---|---|
| DUPLICATE_SUSPECTED | p.4 SPEC-01 기능명세서 업로드 / SPEC-04 요구사항 문서 등록 | 이름만 다르고 세 가지 요구사항이 완전히 같다. | 중복 후보가 두 기능을 연결하고, PDF 등록·검증·비동기 추출의 중복을 설명한다. A→B 또는 B→A 중 한 방향이면 된다. |
| SPLIT_RECOMMENDED | p.10 SHARE-01 협업 결과 전달 | 공유 링크 생성·폐기와 CSV 파일 내보내기가 한 기능에 묶였다. | 최소 두 분리 후보를 제안한다. 예: 공유 링크 관리 / 관련 PR 목록 내보내기. 요구사항마다 기능을 만드는 과분리는 피한다. |
| MISSING_REQUIREMENTS | p.10 SHARE-02 공유 이력 조회 | 제목과 미정 문구만 있고 구체적인 동작·입출력 내용이 없다. | requirements가 빈 배열이며 누락 이슈가 표시된다. 조회 컬럼·필터·보관 기간 등을 지어내지 않는다. |
| SOURCE_REVIEW_REQUIRED | p.10 SHARE-03 공유 링크 만료 갱신 | 첫 문장은 완전하지만 두 번째 문장은 “경우에는”에서 끝나 후속 동작이 없다. | 읽을 수 있는 첫 문장은 유지하고 불완전한 후속 조건을 설명한다. 갱신 허용/거절/오류 응답을 임의로 보완하지 않는다. |
| SOURCE_CONTENT_CONFLICT | p.10 SHARE-04 리포트 파일 다운로드 | 제목은 파일 다운로드인데 실제 요구사항은 밝은/어두운 테마 선택·저장이다. | 제목과 본문 불일치를 설명한다. 요구사항은 테마 내용 그대로 추출하며 파일 다운로드 조건을 만들지 않는다. |

분리 대상 원문의 요구사항 순서는 공유 링크 생성, 공유 링크 폐기, CSV 다운로드, CSV 포함 필드다. LLM이 이 네 문장을 그대로 유지했다면 분리 배정의 자연스러운 예시는 `[0,1]` / `[2,3]`이다. 실제로 문장을 나누거나 합치면 인덱스 수와 값도 달라지므로, **실제 응답의 requirements 전체가 누락·중복 없이 한 번씩 배정됐는지** 검사한다.

### 평가 시 주의

- 32는 원문 항목 수이지 추출 결과 개수를 무조건 32로 강제하는 정답이 아니다. 기능 분해·명칭 정리 때문에 달라질 수 있다. 다만 완전 중복 기능을 조용히 합치거나 미완성 항목을 누락하면 이슈 검토 UX를 시험할 수 없으므로 별도 기록한다.
- 현재 프롬프트의 “제목만으로 기능을 만들지 않음”과 “제목+미정이면 MISSING_REQUIREMENTS” 규칙에는 경계가 있다. SHARE-02가 통째로 누락되면 **누락 이슈 탐지 실패 또는 규칙 우선순위 문제**로 기록한다. requirements에 “추후 작성” 한 줄을 만들어 정상 처리하는 것도 기대와 다르다.
- LLM은 원문의 기능명을 바꿀 수 있다. 원문 ID는 추출 ID나 DB ID와 동일하지 않으므로 이름·요구사항·페이지로 대응시킨다.
- 이슈 문구에 원문 코드(SPEC-01 등)를 그대로 쓰기보다 사용자가 이해할 수 있는 기능명을 사용하는지 확인한다.
- SOURCE_CONTENT_CONFLICT를 놓친 채 SHARE-04의 이름만 “테마 설정”으로 정리하면 원문 충돌이 사용자에게 숨겨지는 것이다.
- 합성 입력도 탐지를 보장하지 않는다. 동일 PDF를 2~3회 분석해 누락·과탐·제안 안정성을 기록한다. 호출 비용이 발생하므로 직접 실행 여부를 선택한다.

REV-04의 병합/분리처럼 같은 검토 목적 안에서도 모델이 독립 목적을 세분화할 여지는 있다. 표에 없는 추가 이슈는 무조건 오답으로 세지 말고 원문과 근거를 보고 판정한다.

## 3. 섹션·페이지·원문 확인

| 섹션 | 기대 물리 페이지 범위 |
|---|---|
| 회원 및 인증 | 2 |
| 프로젝트와 저장소 | 3 |
| 기능명세 등록 및 분석 | 4 |
| 기능목록 검토 | 5 |
| PR 수집 및 분석 | 6 |
| 기능대조 | 7~9 |
| 공유 및 내보내기 | 10 |

- 표지와 목차(p.1)의 제목 재등장을 기능의 직접 근거 페이지로 사용하지 않는지 확인한다.
- MATCH-02만 직접 근거가 p.7~8에 걸친다. MATCH-01은 p.7, MATCH-03·04는 p.8, MATCH-05·06·07은 p.9다.
- “기능대조 (계속)”을 불필요하게 별도 섹션으로 나누지 않는지 확인한다.
- originalText가 원문 문장을 보존하는지 확인한다.
- 현재 백엔드는 LLM 원응답을 정규화한다. 중복 대상 ID나 분리 요구사항 인덱스가 잘못되면 이슈/제안이 제거될 수 있다. 저장된 API 응답에서 배지가 없다는 사실만으로 모델이 처음부터 이슈를 생성하지 않았다고 단정하지 않는다. 원응답을 안전하게 확인할 수 있는 개발 테스트와 정규화 결과를 비교한다.

## 4. 수동 테스트 순서

1. 테스트용 **프로젝트**를 새로 만든다. 테스트용 GitHub 저장소를 새로 만들 필요는 없다.
2. 접근 권한이 있는 기존 `Galpiii/backend` 저장소를 연결하고 외부 AI 전송에 동의한다.
3. 위 PDF를 기능명세서로 업로드하고 추출 완료를 기다린다. 실제 사용 중인 프로젝트에서 교체하면 기존 기능/연결이 삭제될 수 있으므로 독립 프로젝트를 권장한다.
4. 검토를 수정하기 **전에** 기능 목록·특이사항·후보·요구사항·페이지 결과를 저장하거나 캡처한다.
5. PR 수집과 PR 요약을 모두 완료한다. 현재 MVP는 병합된 PR만 수집한다.
6. 첫 대조는 일부 기능을 미확인 상태로 두고 실행한다. 미확인 표시와 “추가 확인 필요” 필터를 확인한다.
7. 중복 후보 병합, 분리 제안 적용, 미완성 기능 제거/수정 등 검토 동작을 각각 확인한다. 내용이 바뀌면 재대조가 필요하다. 단순 승인만 했을 때 결과가 유지되는지도 구분한다.
8. 기능별 관련 PR을 확인하고, PR 다중 직접 연결 및 연결 삭제를 수행한다. 직접 연결은 재대조 후 유지되고 연결 삭제는 GitHub PR을 지우지 않아야 한다.

## 5. 기존 저장소와 PR 매칭 평가

| 명세 범위 | 찾아볼 PR 작업 근거 |
|---|---|
| AUTH-01~04 | GitHub OAuth, 세션 갱신, 로그아웃, 외부 AI 전송 동의 |
| PROJ-01 / REPO-01~04 | 프로젝트 관리, GitHub App 설치·저장소 연결·해제 |
| SPEC-01~04 | PDF 업로드·검증, 비동기 추출, 기능명세서 재업로드 |
| REV-01~04 | 기능 검토 목록·수정·승인·병합·분리 |
| PR-01~04 | PR 수집, PR 요약 워커, 목록·상세 조회 |
| MATCH-01~07 | 이번 기능대조 개발 내용. GitHub에 관련 PR이 병합되어 수집되기 전에는 근거가 없을 수 있다. |
| SHARE-01~04 | 확장/결함 사례. 현재 백엔드의 구현 근거를 단정하지 말고 실제 PR 내용과 대조한다. |

**로컬 파일 또는 브랜치에 코드가 있다고 해서 PR 분석 대상에 포함되는 것은 아니다.** 푸시되지 않은 변경, 아직 병합하지 않은 PR, 설정한 수집 범위 밖 PR은 이번 대조에서 근거로 쓸 수 없다. 이 PDF 작성 과정에서는 GitHub의 현재 PR 목록을 실시간 조회하지 않았으므로 특정 PR 번호를 정답으로 고정하지 않았다.

- “로그인”과 “프로젝트 공유”처럼 사용자 목적이 다른 기능을 단순한 기술 키워드 때문에 연결하면 과매칭으로 기록한다.
- SPEC-01과 SPEC-04가 검토 전 같은 PR에 매칭되는 것은 자연스럽다. 두 기능에 연결됐다고 동일 PR을 전체 PR 개수에 두 번 세면 안 된다.
- 명세 외 리팩터링·인프라·문서 PR에 연결 기능이 없을 수 있다. 모든 PR이 기능에 매칭돼야 성공인 것은 아니다.
- 관련 PR이 없다는 사실은 미구현의 증명이 아니다. 제목·본문·요약 부족이나 수집 범위 때문에 놓쳤을 수 있다.
